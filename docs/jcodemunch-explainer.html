jCodeMunch-MCP — what it does, in this repo

A plain-English explainer of the code-indexing tool we installed on latino-events. Everything below is written from what the tool actually did when run here on 2026-07-01 — not from its marketing README.

One-line summary. It is an MCP server that parses your code into a searchable symbol index (a database of every function, class, CSS rule, etc.), so an AI agent can fetch just the function it needs instead of reading whole files. It saves tokens on big codebases. This repo is small, so the benefit here is modest — see the honest note at the end.

1 · The core idea

Normally, when an AI agent wants to change redeem(), it opens the entire js/redeem.js file, reads all ~120 lines, finds the function, and works from there. Multiply that across a large project and it burns a lot of tokens reading code it doesn't need.

jCodeMunch flips this. It reads your whole codebase once and records, for every symbol, exactly where it lives (file + line range + byte offset). After that, the agent can ask "give me the source of redeem" and get back only those 50 lines.

Agent needs generateOfferCode → query the index → index knows: util.ts L7–12 → return just those 6 lines

Privacy note. The index and a copy of your source sit in ~/.code-index/. It's local to your machine (nothing is uploaded by the indexing step). To wipe it completely: jcodemunch-mcp delete-index or just delete the ~/.code-index/ folder.

4 · How it gets used by an agent

Once registered, Claude Code sees it as an MCP server exposing a set of tools (the package advertises 60+; the ones that matter for a repo this size):

Retrieval (the point)

  • search_symbols — find a function/class by name
  • get_symbol_source — fetch just that symbol's code

Structure

  • find_importers — who calls this?
  • get_blast_radius — what breaks if I change it?

Health

  • find_dead_code — unused symbols
  • get_untested_symbols — functions with no tests

Not enabled here

  • background file watcher (auto-reindex) — off
  • Claude Code hooks that intercept your reads — not installed
  • org telemetry / transcript "receipts" — off

The typical loop

1 index once → 2 agent asks search_symbols("redeem") → 3 get_symbol_source returns L50–100 → 4 agent edits, tool re-indexes that one file

5 · How we set it up (deliberately conservative)

We avoided the tool's one-command init because it's aggressive — it edits MCP config, installs Claude Code hooks, and writes its own CLAUDE.md policy. Instead we did the two discrete, reversible steps:

# 1. Installed in an isolated venv (no system changes, no sudo)
.venv/bin/pip install jcodemunch-mcp

# 2. Indexed the repo locally
.venv/bin/jcodemunch-mcp index .

# 3. Registered project-scoped only, watcher OFF, in .mcp.json

To activate: reload Claude Code and approve the jcodemunch server when prompted. To remove everything: delete .venv, .venv-tools, .mcp.json, and ~/.code-index/.

6 · The honest verdict for this repo

Where it helps. The Supabase backend (supabase/functions/) and client JS are real code with real functions — symbol-level retrieval there is legitimately handy, and will matter more as that backend grows.
Where it doesn't. The token-saving payoff scales with codebase size, and this repo is tiny (fits in one context window). It also can't see your HTML, and ~78% of the "symbols" it found are CSS selectors and YAML keys, not code you'd retrieve. So treat this as a trial that pays off if/when the backend or a framework migration grows the codebase — not a must-have today.
